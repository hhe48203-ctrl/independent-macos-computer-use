# Bench v2 修复前后对比总结

[English version](../BENCH_V2_GOAL_SUMMARY.md)

本页汇总 Cua Driver Bench v2 修复目标的前后对比。复测只覆盖少数同种子轮次，条件也与基线不同，因此只能说明逐个种子的变化，不能作为全量验收。逐项证据见 [Bench v2 失败复现记录](BENCH_V2_REMEDIATION.md)。

## 结论

在已复测的 9 个后台种子中，4 个达到综合通过（任务通过、GUI-only 和 A22 八项全满足），分别是 G02、G04、IR-03 和 IR-04。基线中这 9 个种子均未综合通过。前台条件的 MB-10 和 MB-11 各复测一个种子，均由 0.10 和 0.05 升至 1.00。MB-09、IR-02 和 G03 的分数未变。IR-01 `147201` 的分数不变，A22 从 8/8 降至 4/8，因为测试应用打开原生 sheet 时自行激活，抢走了哨兵焦点。所有复测轮次均满足 GUI-only。其余 35 个基线种子未复测。

`493373c` 是本次收尾提交。它让原生 helper 在 `CU_PUBLIC_API_ONLY=1` 且设置了 `CU_BACKGROUND_WITNESS_PID` 时，于后台输入开始前要求前台应用和系统 AX 焦点均属于初始哨兵，否则返回 `BENCH_WITNESS_FOCUS_CHANGED`，不发送输入。基准 MCP 收到该错误后同样停止后续输入。该提交通过了 `npm run check:native` 编译和回归测试，但尚无桌面实测或 Pi 复测。

## 已知限制

仅公开 API 下仍有四项限制：MB-09 原生表格行拖放、G03 GnuCash 正式对账、IR-01/02 关闭状态的原生下拉框选值，以及 IR-01 Next 打开 sheet 时的换序和应用自激活。前三项在投递前拒绝。第四项无法提前识别，驱动返回错误、不报告成功，基准随后停止该轮输入，A22 按实测失败计分。详情和上游对照见[失败复现记录中的“仅公开 API 的已知限制”](BENCH_V2_REMEDIATION.md#仅公开-api-的已知限制)。

此外，G03 仅公开 API 的轮次无法在 GnuCash 账户树中导航，因为 Accounts 窗口只公开七个 AX 节点。GnuCash 预检按控件标签 Reconcile 识别对账入口，属于应用级规则，不涉及题目答案。

## 下一步全量验收建议

1. 冻结一个提交，记录 `native_sha256` 和 `code_sha256`，验收期间不改代码。
2. 在预留的已解锁桌面上，以 `--public-api-only`、固定 thinking 档位和 `--seed 2026` 运行完整计划：`npm run bench:v2 -- --run --tasks v2 --condition both --runs 5 --allow-multi-app --public-api-only`，共 90 轮。按阶段拆分时用 `--resume` 续跑，基础设施尝试另行记录。
3. 开跑前确认 OpenAI 额度足够完成整组。额度耗尽的轮次记为基础设施错误，恢复后续跑，不计入分数。
4. 报告与基线逐种子配对，列出任务通过、GUI-only、A22 八项、`driver_isolation` 和综合通过。说明 thinking 档位与基线不同。若要单独衡量驱动的贡献，可再跑一组 thinking `low`，或关闭运行器操作引导做消融对照。
5. 全量结果之外，按 [验证记录](VALIDATION.md) 另做真人并发验收和发布归档验收。离屏测试、桌面测试和真人试验覆盖的行为各不相同。
